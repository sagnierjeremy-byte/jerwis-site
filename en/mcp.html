What you see

In the app, it's called
a connector.

In one sentence

A connector plugs the AI into an app you already use (your inbox, your Drive, your calendar) so it can read and act there while it works on a task. MCP is the standard port that lets these links be built once and for all, instead of rebuilding one for every AI.

Without a connector, you paste an email or a spreadsheet into the conversation. With a connector, you write "go and get it" and the AI finds it in your account by itself. You install nothing technical and you don't write a single line of code.

Claude app

Claude's connectors

Where · in the Customize menu, under Connectors.

What you connect · Google Drive, Gmail, Microsoft 365, Slack and others. Connected apps work while Claude carries out a task, including in a folder you've opened to it.

Try this · "Find last quarter's board deck in my Drive and summarize what changed since."

ChatGPT · Work mode

ChatGPT in Work mode

Where · in the ChatGPT desktop app, switch to Work mode.

What it does · Work takes on a whole task and hands back a document, a spreadsheet, a presentation, a report or a site. It can use your files and your apps, with your permission.

Good to know · the messages and the task's context may be saved in the cloud. Keep that in mind for sensitive documents.

Definition

So what is MCP,
exactly?

In one sentence

MCP, short for Model Context Protocol, is an open standard created by Anthropic that lets any language model connect the same way to tools, databases and external services. Instead of writing a custom integration between every AI and every tool, you write an MCP server once, and every compatible client can use it.

The analogy you hear everywhere is USB-C. MCP is to AI what USB-C is to hardware: a universal standard port. Before USB-C, every brand had its own cable, one for Apple, one for Samsung, one for Sony, not to mention the old round jacks. Today you plug a USB-C cable into any recent phone and it just works. MCP does the same thing for AI and its tools.

Why MCP was created

Before MCP, every AI vendor had its own format for plugging in tools. OpenAI had function calling, Anthropic had its Tools API, Google had function declarations, Cohere had connectors. The concrete result: if you wanted an assistant to read your database and write to your Notion, you had to write the integration three times, once for ChatGPT, once for Claude, once for Gemini. Three codebases to maintain, three formats, three learning curves.

Anthropic opened the code and the specification as open source in the modelcontextprotocol GitHub organization. Anyone can write a server, publish it, use it, fork it. And the bet paid off: code editors like Cursor, Continue, Cline and Windsurf adopted it, OpenAI followed, and today you mostly meet it under the name connector, inside the apps. MCP has become the de facto standard for plugging AI into tools.

What MCP is not

MCP is not an AI model. It's not a competitor to Claude, GPT or Gemini. It's a layer on top, independent of the model. You can use MCP with Claude, GPT, Gemini, Mistral, or a local model through Ollama, as long as your client supports the protocol.

It's not an agent framework either. MCP doesn't plan actions or decide what to do next. It defines how an agent can discover and call tools. The orchestration logic stays with the model (or with the framework driving the model, like LangChain, LlamaIndex or Mastra).

To go deeper on the definition, I also wrote a short entry in the glossary: MCP, the simple definition. And the parent concept to understand is tool use / function calling, which describes a model's ability to call a tool instead of only replying with text.

Architecture

How MCP works
under the hood.

MCP relies on a classic client-server architecture, carried over JSON-RPC. On the client side, you have the application that hosts the model (the Claude app, ChatGPT, Cursor, etc.). On the server side, you have an independent process that exposes capabilities to the client. The two talk in JSON-RPC, either locally over stdio or remotely over HTTP.

The 3 kinds of capabilities

An MCP server exposes three broad categories of capabilities, meaning three kinds of things it makes available to the client.

  • Resources (data) · content the server exposes for reading: files, database rows, web pages, CRM content. The client can list them and load them into the model's context.
  • Tools (actions) · functions the model can call to act: write a file, open a GitHub issue, send a Slack message, run a SQL query. It's the equivalent of function calling, but standardized.
  • Prompts (templates) · prewritten prompt templates the user or the model can invoke as a shortcut. Handy for repetitive tasks.

Stdio vs HTTP: two transports

The protocol supports two transport modes depending on the context.

Stdio (standard input/output) is the local mode. The client launches the server as a subprocess and the two communicate over stdin/stdout. It's the default for servers that run on your machine (files, a local database, personal scripts). The upside: no network, maximum security, zero latency.

HTTP ("Streamable HTTP" in the current specification) is the remote mode. The server runs on another machine and the client connects over the network. It's what you use for services that need to stay centralized: a server shared across a team, a SaaS integration, a cloud connector. Most of the connectors you add in a few clicks in the apps work this way, with the server running at the vendor, not on your computer.

The detail that changes everything: automatic discovery

When an MCP client connects to a server, it starts by asking for the list of its capabilities. The model then receives a structured description of every available tool, resource and prompt. No need to hardcode tools in the system prompt: the AI discovers what it can do each time it connects. That's what makes MCP truly portable.

Ecosystem

The popular MCP
servers in 2026.

The MCP ecosystem grew fast. The modelcontextprotocol GitHub organization keeps a handful of reference servers (Filesystem, Fetch, Git, Memory, Time…), and more and more vendors publish their own official server. The community has published hundreds more. Here are the ones I see come up in every serious conversation about AI agents.

The most used day to day

  • Filesystem · read, write and list local files. You give access to one specific folder, and the AI can work with your notes, your documents, your projects. In the Claude app, you already get the equivalent without installing anything: you open a folder to it.
  • GitHub · manage issues, pull requests, branches, repos. GitHub publishes its own official server. Handy for automated code reviews.
  • Google Drive / Notion / Slack · read and write in your collaborative work tools. In the Claude app, Google Drive, Gmail, Microsoft 365 and Slack are among the ready-made connectors. Notion is especially useful for knowledge bases.
  • PostgreSQL / SQLite · run SQL queries for reading (and sometimes writing, depending on the setup) against a database. Widely used in data analysis.
  • Playwright · drive a browser. The AI can open pages, click, extract content, take screenshots. It took over from the old Puppeteer server, now archived.
  • Brave Search / Tavily / Exa · run web searches from an agent you build. Brave publishes its official server, Tavily and Exa are paid but return content better structured for AI. In the apps, web search is already built in.

The custom servers I see popping up

Beyond the reference servers, the community publishes MCP servers for pretty much everything. Linear, Jira, Trello for project management. Stripe, PayPal for payments. HubSpot, Pipedrive for CRM. If a service has a public API, there's a good chance an MCP server already exists for it. The reflex before building one: first check your app's list of connectors, then the modelcontextprotocol/servers GitHub repo and community lists like awesome-mcp-servers.

And of course, you can always make your own. For my own needs (agents that run my site, interact with my newsletter, watch my releases), I've set up a few minimal MCP servers in TypeScript, with the AI's help. We'll see how a bit further down, in the dedicated section.

Be careful which servers you install

An MCP server is code that runs with access to whatever you give it. A badly written or malicious server can read your files, exfiltrate your secrets or post in your name. Golden rule: never install a server whose source you haven't checked. The MCP project's reference servers and the ones published by the vendor itself (GitHub, Notion, Brave…) are the safest. For the rest, look at the repo, who maintains it, and the date of the last update.

Comparison

MCP vs Function Calling
vs Tools API.

When you discover MCP, the first question that comes up is: how is it different from function calling? It's a good question, because the three concepts look alike on the surface. Here's how I tell them apart.

Function Calling (OpenAI, 2023)

Function calling is a model's ability to choose to call a function instead of generating text. OpenAI popularized the concept in June 2023 with GPT-3.5 and then GPT-4. You describe your functions to the model in a JSON format specific to OpenAI, and the model can decide to call them with arguments.

Limitation: the format is specific to OpenAI. If you want to do the same thing with Claude or Gemini, you rewrite your integration.

Tools API (Anthropic, 2024)

The Tools API is Anthropic's equivalent of function calling, launched in early 2024. Same idea, slightly different format, natively supported by Claude models. Same principle as function calling, with its own specification.

Same limitation: the format is specific to Anthropic. Not portable to other models.

MCP (Anthropic, November 2024)

MCP is an open standard on top of all of that. In practice, your MCP server exposes tools (which look a lot like function calls), resources and prompts. The MCP client translates those tools into the format of whatever model it uses. If you switch models tomorrow, your server doesn't move.

So in practice: function calling and the Tools API are low-level features, specific to each model. MCP is a higher-level protocol that sits on top. They coexist; they don't replace each other. Under the hood, an MCP client always uses function calling or the Tools API to talk to its model.

Build

How to build your
first MCP server.

This part is for those who want to make their own link. To use the existing connectors, you don't need it. I won't give you the full tutorial here: the official docs at modelcontextprotocol.io do it very well, and the tech moves too fast for a static page to stay accurate on the details. Here's the general outline to get started.

Pick your language: Python or TypeScript

There are two official SDKs: Python and TypeScript. Both are equally mature.

You choose based on your habits. If you live in the JavaScript ecosystem, go with TypeScript. If you do data or AI work in Python, go with Python. For a first server, both work just as well, and the code is of similar complexity.

The 4 steps to your first server

01

Initialize your project

Each official SDK provides a starter template: the @modelcontextprotocol/sdk package in TypeScript, the mcp package in Python. The official docs give the exact steps for each.

You end up with a folder holding the server skeleton, the dependencies and a starting point ready to run.

02

Define your capabilities

You decide what your server exposes. The three categories: tools (actions), resources (data), prompts (templates). For a first server, start with one or two simple tools, for example a tool that returns the weather for a city, or one that lists the files in a folder.

For each capability, you declare a name, a description (the AI uses it to understand when to call it) and a JSON schema for its arguments.

03

Test locally with MCP Inspector

The project provides a testing tool called MCP Inspector that launches your server and shows it in a web page. You see the list of capabilities, you can call your tools by hand and check the responses.

It's the most worthwhile step. Testing before plugging into a real client saves you a huge amount of time finding bugs.

04

Plug it into your client

A remote server is added to the Claude app as a custom connector, with its address. A local server is declared in the desktop app's configuration file (~/Library/Application Support/Claude/claude_desktop_config.json on Mac), with the launch command, the arguments and the environment variables.

You restart the app. If everything is set up correctly, your server shows up in the list of available tools and the AI can call it. You ask it in plain English to use your tool, and you see whether the magic happens.

To go further on the code

The modelcontextprotocol/servers repo holds the reference servers, in TypeScript and Python. The best way to learn is to read the code of the Filesystem server or the Fetch server: they're simple, well commented, and you can draw on them for your own server.

Who it's for

Who it's useful for
(and who not).

Case #1

Developer building agents

Yes, all the way. MCP is designed for you. You write your own servers, you integrate the official ones, you build agents that work in the Claude app, in Cursor or in Claude Code, the developer tool, without rewriting your integration. It's the protocol's original target.

Case #2

Founder or freelancer

Yes, without coding anything. You connect the connectors you need (Google Drive, Gmail, Microsoft 365, Slack) in the Claude app, or you switch ChatGPT to Work mode. With an open folder and two or three connectors, the AI works on your real documents. That's where I recommend starting.

Case #3

Everyday user

Yes, often without knowing it. When you connect your inbox or your Drive in the Claude app, you're already using this kind of connector. You don't need to learn the word MCP, just to choose what you connect and to check what the AI does in your name.

Case #4

SMB running a chatbot

Scope it before you dive in. Connecting your customer chatbot to your CRM or product catalog through MCP is technically possible, but it's a real development project. Specialized solutions (Voiceflow, Botpress, industry platforms) remain simpler to set up. MCP becomes relevant when you move past the consumer chatbot and build a custom agent.

My honest take: for most people, MCP hides behind connectors, and that's just fine. You benefit from it as soon as you connect an app to the AI. The word itself is mostly useful to people who build agents, integrations or automations. For them, it's a gift.

FAQ

MCP FAQ.

The 12 questions I asked myself when I discovered MCP, and that people still ask me today. Short, direct answers, honest about what I don't know.

What is MCP, in one sentence?

MCP, short for Model Context Protocol, is an open standard created by Anthropic that lets any language model connect the same way to tools, databases and external services. In the apps, you meet it under the name connector. Think of it as USB-C for AI: one port to plug everything in.

Who invented MCP?

MCP was designed and published by Anthropic, the company behind Claude, and its code is open source in the modelcontextprotocol GitHub organization. Since late 2025 it has been governed by an independent foundation, the Agentic AI Foundation, hosted by the Linux Foundation. OpenAI, code editors like Cursor and the community have adopted it, which makes it a de facto standard.

Why is everyone talking about it?

Because it's the first credible attempt to standardize how AI plugs into tools. Before MCP, every AI vendor had its own format (OpenAI's function calling, Anthropic's Tools API, Google's function declarations), and developers rewrote the same integrations three times. MCP unifies all of that. And in November 2026 you benefit without knowing it: when you connect Gmail or Google Drive in the Claude app, you're using this kind of connector.

Is MCP open source?

Yes. The specification, the official SDKs (Python and TypeScript) and the reference servers are published as open source on GitHub, in the modelcontextprotocol organization. Anyone can write a server, publish it, fork it. And since the protocol was handed to a foundation, no single company has exclusive control over it.

MCP vs function calling: what's the difference?

Function calling is a feature specific to each model (OpenAI has its format, Anthropic its own, Google its own). MCP is an open protocol that sits on top. In practice: with function calling, you write one integration per LLM; with MCP, you write a server once and any compatible client can use it. MCP is the standard; function calling is the model's internal implementation.

How do I connect a connector in the Claude app?

In the Claude app, open Customize, then Connectors, pick the app (Google Drive, Gmail, Microsoft 365, Slack…) and connect your account. From then on, Claude uses it while it works on a task. In ChatGPT, switch the desktop app to Work mode: it can use your files and apps, with your permission. To install an MCP server by hand, see the For the curious note at the bottom of the page.

Which apps use MCP in 2026?

On Anthropic's side, the Claude app, with its connectors. On OpenAI's side, support was announced back in 2025. Among code editors, Cursor, Continue, Cline and Zed support it. The list moves fast: most serious AI clients have made the switch.

Is MCP secure?

The protocol itself is secure by design: each server runs in its own process, capabilities are declared explicitly, and the client can filter the tools it exposes. The real risk is what you connect. A connector acts with your account's permissions, and a badly written or malicious server can read your files or leak your secrets. Golden rule: only connect what the task needs, and only from trusted sources.

How do I write my own MCP server?

You pick your language (Python or TypeScript, the official SDKs cover both), start from the official template, declare the capabilities (tools, resources, prompts) your server exposes, implement their handlers, then connect your client. The modelcontextprotocol.io docs have a full tutorial. For a simple first server, plan on one to two hours.

MCP vs LangChain Tools: what's the difference?

LangChain Tools is an abstraction layer on the framework side (you use LangChain to orchestrate your agent and its tools). MCP is a communication protocol between client and server. The two can coexist: you can expose an MCP server that a LangChain agent then consumes, or the other way round. MCP is lower level and more universal; LangChain is higher level and tied to its ecosystem.

What are MCP's known limitations?

Three limits I see in November 2026. Documentation is still uneven from one server to the next. Security partly depends on your vigilance: for a server found outside your app's list of connectors, you have to check who wrote it. And plugging in a server that isn't on that list is still technical. The ready-made connectors in the apps solve a good part of that last point.

How do I keep up with MCP?

The specification and its public roadmap live on modelcontextprotocol.io and in the modelcontextprotocol GitHub organization. I'd rather point you there than freeze announcements here that change every quarter. And I flag the changes that matter in my Friday letter.
